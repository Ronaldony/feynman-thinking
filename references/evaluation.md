# 행동 평가와 회귀 테스트

이 스킬의 이름, 문체 또는 체크리스트 완성도가 아니라 **AI의 관찰 가능한 작업 행동과 과제 결과가 실제로 달라지는지** 평가한다.

## 1. 검증하려는 주장

평가는 다음 네 주장을 분리한다.

1. **발동 가능성**: 필요한 과제에서 스킬이 선택되고 불필요한 과제에서는 선택되지 않는다.
2. **과정 준수**: 이름 벗기기, 모델·재표현, 구체적 작업, 공격, 수정의 핵심 루프가 실제로 나타난다.
3. **결과 개선**: 숨은 결함 탐지, 정확성, 의사결정 품질과 검토 가능성이 기준선보다 좋아진다.
4. **파인만 행동 특이성**: 일반적인 비판적 사고 지침보다 재표현·직접 계산·경계 사례·판별 검사·수정 행동을 더 잘 유도한다.

문서가 잘 작성되었다는 사실은 위 주장을 증명하지 않는다.

## 2. 평가 조건

동일한 held-out 과제를 다음 조건에서 실행한다.

| 조건 | 환경과 프롬프트 | 확인하려는 것 |
|---|---|---|
| A. baseline | 스킬이 없거나 비활성화된 환경, 원문 프롬프트 | 기본 모델 성능 |
| B. generic | 스킬이 없거나 비활성화된 환경, 일반 비판적 사고 지침 추가 | 일반적인 “신중한 분석” 효과 |
| C. feynman-explicit | 스킬 설치 환경, `$feynman-thinking` 명시 호출 | 스킬을 읽었을 때의 수행 가능성 |
| D. feynman-implicit | 스킬 설치 환경, 자연스러운 복합 과제 | description 기반 자동 발동 |

A와 D는 프롬프트가 비슷할 수 있으므로 **스킬 설치·활성화 환경을 분리**하고 실행 추적에서 실제 로드 여부를 확인한다.

각 조건은 가능한 경우 같은 모델·버전·도구·시간 제한에서 최소 3회 반복한다. 실행 순서는 무작위화하고 평가자는 조건명을 보지 못하게 한다.

## 3. 평가 자료

- 발동 평가: [../evals/trigger-cases.csv](../evals/trigger-cases.csv)
- 추론 행동 평가: [../evals/reasoning-cases.jsonl](../evals/reasoning-cases.jsonl)

평가 사례를 스킬 본문에 복사하거나 모델에게 기대 행동을 정답처럼 노출하지 않는다. 개편에 사용한 사례와 최종 성능 보고에 사용하는 held-out 사례를 분리한다.

## 4. 발동 평가

다음을 따로 측정한다.

- 명시 호출 성공률
- 암묵 호출 정밀도: 실제 발동 중 필요한 발동의 비율
- 암묵 호출 재현율: 필요한 과제 중 실제 발동한 비율
- 단순 작업 오탐률
- 파인만 전기·말투 요청 오탐률
- 스킬이 선택됐지만 본문 또는 필요한 참조 파일을 읽지 않은 비율

`trigger-cases.csv`는 기대값 데이터일 뿐 실행 결과가 아니다. 실제 trace와 비교해 오탐·미탐을 기록한다.

## 5. 과정 준수 평가

### 5.1 파인만 핵심 지표

각 항목은 `0 / 1 / 2 / N/A`로 평가한다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 이름 벗기기 | 용어를 반복 | 일부 작동 정의 | 대상·입력·출력·관찰량으로 문제를 재구성 |
| 메커니즘 | 설명 없는 결론 | 부분 경로 | 입력에서 출력까지 작동 관계가 명확 |
| 대안 표현 | 첫 표현에 고착 | 대안 언급 | 다른 표현을 실제로 만들어 비교·선택 |
| 구체적 작업 | 제안만 나열 | 작은 예시 또는 불완전 작업 | 유도·계산·실행·자료 확인을 재검토 가능하게 수행 |
| 정량 감각 | 근거 없는 숫자 또는 없음 | 단위·규모 일부 | 단위·규모·경계·민감도를 적절히 검사 |
| 경쟁 모델 | 허수아비 또는 없음 | 가능한 대안 언급 | 같은 관찰을 설명하는 강한 대안 모델 |
| 판별 검사 | 결론을 못 바꾸는 검사 | 실행 가능한 검사 설계 | 수행되었거나 결과별 수정 규칙이 명확한 고판별력 검사 |
| 수정 루프 | 반대 증거를 무시 | 한계·확신만 약화 | 모델·범위·결론을 실제로 되돌려 수정 |
| 쉬움-정밀 동치 | 쉬운 말 또는 전문 설명 한쪽만 | 둘 다 있으나 연결 약함 | 쉬운 설명과 정밀 근거가 같은 메커니즘을 보존 |
| 불확실성 교정 | 과도한 확신 | 일반 면책 문구 | 미지·범위·변경 조건과 확신이 연결 |

`N/A`는 해당 주장 유형에서 실질적으로 적용되지 않을 때만 사용하며 평균 계산에서 제외한다.

### 5.2 작업 증거 판정

다음은 구체적 작업으로 인정할 수 있다.

- 단계가 확인 가능한 유도·계산
- 단위와 입력이 있는 추정
- 실행 로그가 있는 코드·테스트·벤치마크
- 행과 열의 의미가 명확한 데이터 비교
- 출처의 날짜·버전·원주장을 직접 대조한 기록
- 변수와 교란 경로가 명확한 인과 도식
- 사전 통과 기준이 있는 실험·프로토타입

“검증해야 한다”, “자료가 필요하다”는 제안만으로는 인정하지 않는다.

## 6. 결과 품질 평가

과정 점수와 별도로 과제별 결과를 평가한다.

- 숨겨진 결함 또는 핵심 전제 탐지
- 사실·논리 오류 수
- 기준선 대비 정답 또는 의사결정 품질
- 반대 증거 포함률
- 결론의 범위와 실제 근거의 일치
- 사용자가 재현·재검토할 수 있는 정도
- 실행 단계의 구체성
- 토큰·시간·도구 호출 비용
- 불필요한 장문·체크리스트 비용

총점만 보지 말고 핵심 결함을 놓친 경우를 별도 회귀 실패로 기록한다.

## 7. 하드 게이트

다음 중 하나가 발생하면 총점과 무관하게 실패 후보로 분류한다.

- 확인되지 않은 사실이나 실행 결과를 수행한 것처럼 조작
- 태그와 제목만 있고 실제 작업 증거가 없음
- 어느 결과에서도 결론을 바꾸지 않는 검사를 강한 검증으로 제시
- 불리한 증거가 있는데 결론·범위·확신에 아무 영향이 없음
- 수학적 사례를 증명으로 오인하거나 정의역 밖 결론을 일반화
- 인간·사회 문제를 이해관계자·제도·윤리 없이 물리 변수로 과도하게 환원
- 고위험 작업에서 최신 권위 자료나 전문가 검토 필요성을 누락
- 스킬의 사용 자체를 파인만식 또는 정확성의 증거로 주장

## 8. 일반 비판적 사고와의 비교

C 조건이 A보다 나은 것만으로는 파인만 특이성을 입증할 수 없다. B와 비교해 다음 지표에서 추가 효과가 있는지 본다.

- 작동 정의로의 재표현률
- 독립적인 대안 표현 생성률
- 직접 계산·추정·작은 사례 수행률
- 경계·극한·실패 입력 사용률
- 경쟁 모델을 실제로 구별하는 검사 비율
- 불리한 결과에 따른 모델 수정률
- 쉬운 설명과 정밀 근거의 일치도

B와 C가 비슷하면 스킬을 더 짧은 일반 검증 스킬로 축소하거나, 파인만 고유 행동을 강화할지 검토한다.

## 9. 실행 도구

`run_eval.py`는 사례와 조건을 조합해 외부 에이전트 명령에 프롬프트를 표준 입력으로 전달하고, stdout·stderr·종료 상태·소요 시간·최종 메시지를 JSONL로 기록한다.

```bash
python scripts/run_eval.py \
  --cases evals/reasoning-cases.jsonl \
  --condition feynman-explicit \
  --repeats 3 \
  --command "codex exec --json -" \
  --environment "Codex CLI, skill installed"
```

Codex의 비대화식 실행에서는 `codex exec -`가 표준 입력을 전체 프롬프트로 사용하고 `--json`이 JSONL trace를 출력한다. 다른 에이전트 CLI도 표준 입력을 읽는 명령이면 사용할 수 있다.

실행 전 프롬프트만 확인하려면 다음을 사용한다.

```bash
python scripts/run_eval.py --condition all --dry-run
```

`prepare_blind_review.py`는 조건명을 숨긴 검토 샘플, 채점 CSV와 별도 정답 키를 만든다.

```bash
python scripts/prepare_blind_review.py \
  --input evals/results/run.jsonl \
  --rubric evals/grading-rubric.json \
  --output-dir evals/review/run
```

자동 키워드 점수만으로 최종 품질을 판정하지 않는다. 구조 검사는 누락 탐지에 사용하고, 의미·정확성·판별력은 블라인드 평가자가 채점한다.

## 10. 결과 보고

평가 보고에는 최소한 다음을 남긴다.

```text
스킬 버전과 커밋:
모델·버전:
실행 환경·도구:
사례 집합과 held-out 여부:
조건별 반복 수:
발동 정밀도·재현율:
조건별 과정 점수:
조건별 과제 결과:
하드 게이트 실패:
비용:
결론:
가장 큰 한계:
다음 회귀 사례:
```

평균뿐 아니라 사례별 분산과 최악 실패를 보존한다. 모델·버전·도구가 바뀌면 결과를 같은 모집단으로 섞지 않는다.

## 11. 버전 관리

실제 실패 사례를 발견하면 다음을 남긴다.

```text
프롬프트:
기대 행동:
실제 행동:
실패 원인:
수정한 규칙:
새 회귀 검사:
수정 전후 비교:
```

버전은 최소한 하나의 실제 실패가 해결되었거나 명확한 기능이 추가되었을 때 변경한다. 평가 결과가 개선되지 않거나 비용 대비 효과가 낮으면 규칙을 줄이거나 삭제한다.
