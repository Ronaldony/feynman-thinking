# 행동 평가와 회귀 테스트

이 스킬은 이름이나 문체가 아니라 **관찰 가능한 작업 행동과 결과 향상**으로 평가한다. 문서가 올바른 형식인지, 모델이 스킬을 선택하는지, 절차를 실제로 수행하는지, 일반적인 비판적 사고 지침보다 추가 가치가 있는지를 분리해 검증한다.

## 1. 네 단계의 증거

| 단계 | 질문 | 증거 |
|---|---|---|
| 패키지 검증 | 스킬이 로드 가능한가? | frontmatter, 링크, 파일 구조, 스크립트 검사 |
| 발동 검증 | 필요한 과제에서 선택되고 불필요한 과제에서 억제되는가? | 명시·암묵·문맥·negative-control 실행 추적 |
| 행동 검증 | 모델이 핵심 루프를 실제로 수행하는가? | 실행 trace, 계산·검색·테스트, 산출물과 수정 기록 |
| 효과 검증 | 스킬이 기준선보다 결과를 개선하는가? | A/B/C 반복 비교, 오류·탐지·비용·사용자 효용 |

패키지 validator 통과는 행동이나 성능의 증거가 아니다.

## 2. 비교 조건

동일한 held-out 과제를 최소 다음 세 조건에서 수행한다.

- **A — baseline**: 추가 사고 지침 없이 원래 과제만 제시
- **B — generic**: 일반적인 비판적 사고 지침을 제시하되 파인만식 코어는 사용하지 않음
- **C — feynman**: `$feynman-thinking`을 명시적으로 호출

가능하면 각 조건을 여러 번 실행하고 모델·설정·스킬 커밋 SHA를 기록한다. C가 A보다 좋아도 B와 차이가 없으면 “엄격한 일반 분석”의 효과일 수 있으며, 파인만 특이 효과는 입증되지 않은 것이다.

## 3. 평가 과제 구성

10~20개의 작은 과제로 시작하고 실제 실패가 발견될 때마다 추가한다. 다음 범주를 섞는다.

- 소프트웨어 성능·정확성 주장
- 인과 추론
- 수학·논리
- 근사 모델
- 설계·공학
- 예측
- 연구 종합
- 정책·사회 판단
- 설명·교육

각 과제에는 다음을 저장한다.

```json
{
  "id": "case-id",
  "prompt": "사용자 과제",
  "domain": "software",
  "risk_level": "L1",
  "expected_findings": ["발견해야 할 핵심 결함"],
  "required_behaviors": ["관찰해야 할 작업 행동"],
  "optional_behaviors": ["관련 있을 때만 평가"],
  "hard_failures": ["발생하면 즉시 회귀 실패"],
  "notes": "채점자용 설명"
}
```

평가용 숨은 결함과 기준을 실제 실행 프롬프트에 노출하지 않는다.

## 4. 결과 품질 루브릭

각 항목은 `0 / 1 / 2 / N/A`로 평가한다.

- `0`: 누락 또는 명확한 실패
- `1`: 부분 충족이나 피상적 수행
- `2`: 결론에 영향을 주는 실질적 수행
- `N/A`: 현재 과제에는 적용되지 않음. 이유 필수

`N/A`는 분모에서 제외한다. 과제의 `required_behaviors`에 있는 항목은 `N/A`로 처리할 수 없다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 문제 재정의 | 표면 문장을 반복 | 목표·범위를 일부 보정 | 실제 결정·관찰량·성공·오류 비용이 명확 |
| 실체·메커니즘 | 용어·권위 반복 | 일부 과정 설명 | 입력·상태·관계·출력이 작동 모델로 연결 |
| 독립 표현 | 첫 표현에 고착 | 다른 표현을 언급만 함 | 대안 표현이 숨은 가정이나 귀결을 새로 드러냄 |
| 직접 점검 | 검사 제안만 함 | 단순 사례 또는 정성 점검 | 계산·규모·경계·실행·자료 비교를 실제 수행 |
| 근사 정직성 | 정확과 근사를 혼동 | 근사를 언급 | 정확 기준·버린 정보·범위·오차·실패 신호 연결 |
| 경쟁 모델 | 대안 없음 | 이름만 다른 대안 | 다른 메커니즘과 다른 예측을 가진 모델 비교 |
| 판별 검사 | 지지 사례만 제시 | 일반적 반론·추가 조사 | 결과에 따라 모델 선택이 달라지는 검사 설계·수행 |
| 불리한 증거 반영 | 누락 | 한계 문단만 추가 | 실패·충돌이 결론·범위·확신을 실제 수정 |
| 쉬움-정밀함 연결 | 쉬움 또는 정밀함 한쪽만 | 두 층이 있으나 연결 약함 | 쉬운 설명이 조건·인과·예외를 보존하며 정밀 모델과 일치 |
| 불확실성 교정 | 과도한 확신 | 모호한 주의 문구 | 미검증·충돌·변경 조건과 확신이 연결 |
| 실행 가능성 | 결론만 제시 | 일반적인 다음 단계 | 가장 작은 다음 판별 검사 또는 실행·중단 조건 제시 |
| 효율 | 의례적 장문·반복 | 일부 불필요 절차 | 위험에 맞는 깊이로 치명적 검사에 집중 |

## 5. 파인만 특이 지표

일반적인 좋은 분석과 구별하기 위해 다음 다섯 항목을 별도로 집계한다.

1. **명칭 해체**: 추상 용어를 관찰 가능한 현상과 관계로 바꾸었는가?
2. **독립 재표현**: 기존 설명과 다른 표현이나 최소 모델이 실제 구조를 드러냈는가?
3. **현실 접촉**: 숫자, 경계, 장난감 사례, 직접 계산·실행 중 하나를 수행했는가?
4. **판별 공격**: 경쟁 모델의 다른 예측과 결론을 바꿀 검사를 만들었는가?
5. **수정 후 설명**: 실패를 반영한 모델을 쉬운 설명과 정밀 근거로 함께 전달했는가?

C가 이 지표에서 A와 B보다 일관되게 높지 않다면 파인만식 고유성은 확인되지 않은 것이다.

## 6. 하드 실패

다음 중 하나라도 발생하면 총점과 무관하게 회귀 실패로 기록한다.

- 파인만의 이름이나 인용을 증명으로 사용함
- 실행하지 않은 계산·검색·테스트를 수행했다고 주장함
- 핵심 자료를 만들거나 왜곡함
- 경쟁 모델이 같은 예측을 하는데 판별했다고 주장함
- 불리한 증거를 확인하고도 결론·범위·확신을 전혀 수정하지 않음
- 수학적 사례를 증명으로 오인함
- 고위험 의료·법률·재무·안전 문제에서 최신 자료와 전문가 검토 필요성을 누락함
- 인간·사회 문제를 물리 변수처럼 환원해 이해관계자·인센티브·윤리를 삭제함
- 저위험 과제에서 템플릿을 강제로 모두 채워 결과를 현저히 악화함

## 7. 채점 계산

과제별 일반 점수는 적용 가능한 항목 점수의 합을 최대 가능 점수로 나눈다.

```text
normalized_score = sum(applicable_scores) / (2 × applicable_item_count)
```

별도로 다음을 기록한다.

- 파인만 특이 지표 점수
- 예상 핵심 결함 탐지율
- 사실·논리 오류 수
- 결론이 반대 증거에 따라 수정된 비율
- 미검증 항목의 정직한 표기율
- 입력·출력 토큰과 도구 호출 수
- 사용자가 결정을 재검토할 수 있는 정도

총점 평균만 보지 않는다. 하드 실패와 0점 항목의 패턴을 우선 본다.

## 8. 실행 trace와 최종 답변을 함께 본다

최종 답변의 제목과 키워드만 채점하면 형식 준수가 추론을 가장할 수 있다. 가능한 경우 JSONL trace에서 다음을 확인한다.

- 실제 명령·검색·파일 읽기·계산이 있었는가?
- 같은 검사를 반복하며 소모하지 않았는가?
- 도구 실패를 성공으로 보고하지 않았는가?
- 스킬 사용 조건과 미사용 조건의 자원 비용은 어떠한가?
- 최종 결론이 실행 중 발견된 실패에 따라 바뀌었는가?

정량·의미 채점은 분리한다. 결정적 구조 검사는 코드로, 메커니즘의 타당성과 결론 수정은 구조화된 사람 또는 모델 채점으로 검토한다.

## 9. 저장소 평가 도구

- [../evals/trigger-cases.csv](../evals/trigger-cases.csv): 명시·암묵·문맥·negative-control 발동 사례
- [../evals/reasoning-cases.jsonl](../evals/reasoning-cases.jsonl): 숨은 결함과 기대 행동을 포함한 held-out 과제
- [../evals/grading-schema.json](../evals/grading-schema.json): 구조화된 채점 출력 스키마
- [../scripts/run_evals.py](../scripts/run_evals.py): A/B/C 조건에서 `codex exec --json` trace 수집
- [../scripts/grade_evals.py](../scripts/grade_evals.py): trace의 최종 답변을 루브릭으로 채점하고 조건별 집계
- [../scripts/validate_skill.py](../scripts/validate_skill.py): 패키지·링크·평가 파일 정적 검사

예시:

```bash
python scripts/validate_skill.py
python scripts/run_evals.py --conditions baseline generic feynman --repeats 1
python scripts/grade_evals.py --run-dir evals/results/<run-id>
```

실행 스크립트는 Codex CLI와 유효한 인증을 필요로 한다. 실행되지 않은 평가를 통과했다고 기록하지 않는다.

## 10. 수용 기준

새 버전을 “검증됨”으로 부르기 전에 최소한 다음을 충족한다.

1. 패키지 정적 검증 통과
2. 명시 호출과 주요 암묵 호출 사례가 실제 trace로 확인됨
3. 모든 held-out 과제에서 하드 실패 없음
4. C가 A보다 일반 품질에서 개선됨
5. C가 B보다 파인만 특이 지표에서 개선됨
6. 비용 증가가 품질 개선에 비해 과도하지 않음
7. 실패 사례와 수정 규칙이 회귀 데이터에 추가됨

샘플 수가 작거나 결과가 혼재하면 `예비 검증`, `조건부 유효`, `미검증` 중 하나로 상태를 표시한다. 한 번의 성공 사례로 성능을 일반화하지 않는다.

## 11. 버전 관리

실제 실패를 발견하면 다음을 남긴다.

```text
프롬프트:
비교 조건과 모델:
기대 행동:
실제 행동:
실패 원인:
수정한 규칙:
추가한 회귀 사례:
수정 후 결과:
```

느낌에 따라 버전을 올리지 않는다. 최소 하나의 재현 가능한 실패가 해결되었거나 측정 가능한 기능이 추가되었을 때 변경한다.
