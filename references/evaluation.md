# 행동 평가와 회귀 테스트

이 스킬의 이름, 문체나 체크리스트 완성도가 아니라 **AI의 관찰 가능한 작업 행동과 과제 결과가 실제로 달라지는지** 평가한다.

정적 validator가 통과했다는 사실은 설치 가능한 패키지라는 증거일 뿐, 모델이 스킬을 따르거나 결과 품질이 향상되었다는 증거가 아니다.

## 1. 검증하려는 주장

평가는 다음 네 주장을 분리한다.

1. **발동 가능성**: 필요한 과제에서 스킬이 선택되고 불필요한 과제에서는 선택되지 않는다.
2. **과정 준수**: 이름 제거, 독립 모델, 현실 점검, 판별 공격, 실패 후 수정의 핵심 루프가 실제로 나타난다.
3. **결과 개선**: 숨은 결함 탐지, 정확성, 의사결정 품질과 검토 가능성이 기준선보다 좋아진다.
4. **파인만 행동 특이성**: 일반적인 비판적 사고 지침보다 재표현·직접 계산·경계 사례·판별 검사·수정 행동을 더 잘 유도한다.

한 조건에서 좋아진 항목과 나빠진 항목을 함께 보존한다. 스킬 사용이 모든 과제에서 자동으로 이득이라고 가정하지 않는다.

## 2. 네 가지 비교 조건

동일한 held-out 과제를 다음 조건에서 실행한다.

| 조건 | 스킬 환경 | 후보 프롬프트 | 확인하려는 것 |
|---|---|---|---|
| A. `baseline` | 스킬 없음 | 원문 과제 | 기본 모델 성능 |
| B. `generic` | 스킬 없음 | 일반 비판적 사고 지침 + 원문 | 일반적인 신중함의 효과 |
| C. `feynman` | 스킬 설치 | `$feynman-thinking` 명시 호출 + 원문 | 스킬을 읽었을 때의 수행 가능성 |
| D. `feynman-implicit` | 스킬 설치 | 원문 과제 | description 기반 암묵 발동과 행동 변화 |

A와 D는 후보에게 전달되는 원문이 같다. 따라서 스킬 설치 환경을 분리하고 실행 기록에 `skill_installed`와 `explicit_skill_invocation`을 남긴다. 암묵 발동은 답변에 파인만이라는 단어가 있는지로 판정하지 않는다. 가능한 경우 trace의 스킬 파일 참조와 핵심 행동 점수를 함께 본다.

B와 C를 반드시 비교한다. C가 A보다 좋아도 B와 차이가 없다면 효과가 파인만 특이 행동이 아니라 일반적인 “더 신중하게 생각하라”는 추가 지침에서 온 것일 수 있다.

## 3. 실행 통제

가능한 경우 다음을 고정한다.

- 모델과 Codex CLI 버전
- 같은 도구·권한·sandbox
- 시간 제한과 반복 수
- 평가 사례 버전
- 스킬 커밋과 패키지 digest
- 채점 모델과 채점 프롬프트

각 조건은 최소 3회 반복한다. `--shuffle --seed <정수>`로 실행 순서를 무작위화하고 seed를 기록한다. 평균뿐 아니라 사례별 분산과 최악 실패를 남긴다.

새 모델·CLI·스킬 버전의 결과를 기존 모집단에 조용히 합치지 않는다. 비교가 필요하면 별도 결과 집합으로 실행한다.

개편 중 규칙을 만드는 데 직접 사용한 사례와 최종 성능 보고에 사용하는 held-out 사례를 분리한다. 사례가 반복 노출되면 새 회귀 사례를 추가한다.

## 5. 발동 평가

`trigger-cases.csv`의 기대값과 실제 환경의 trace를 비교한다.

측정 항목:

- 명시 호출 성공률
- 암묵 호출 정밀도: 실제 발동 중 필요한 발동의 비율
- 암묵 호출 재현율: 필요한 과제 중 실제 발동한 비율
- 단순 작업 오탐률
- 전기·말투·인용 요청 오탐률
- 스킬이 설치되었지만 핵심 행동이 나타나지 않은 비율

`trigger-cases.csv`는 기대값 데이터일 뿐 실행 결과가 아니다. 실제 발동 기록과 행동 점수가 없으면 “암묵 발동 검증 완료”라고 쓰지 않는다.

## 6. 과정 준수 루브릭

각 항목은 `0 / 1 / 2 / NA`로 평가한다. `NA`는 해당 주장 유형에 실질적으로 적용되지 않을 때만 사용하며 평균에서 제외한다.

| 차원 | 0점 | 1점 | 2점 |
|---|---|---|---|
| `problem_reframe` | 추상 명칭과 사용자 표현을 반복 | 일부 작동 정의 | 대상·입력·출력·관찰량·성공 기준으로 문제 재구성 |
| `mechanism` | 결론이나 용어만 제시 | 일부 관계만 설명 | 입력에서 출력까지 핵심 작동 경로가 명확 |
| `independent_representation` | 첫 표현에 고착 | 다른 표현을 언급 | 수식·표·상태·인과·장난감 모델을 실제로 만들어 새 구조를 드러냄 |
| `direct_check` | 검사 제안만 나열하거나 수행한 척함 | 작은 예시·부분 계산 | 입력·유도·결과가 재검토 가능한 계산·실행·자료 대조 수행 |
| `approximation_honesty` | 근사와 정확 관계를 혼동 | 근사만 언급 | 정확한 기준·버린 정보·오차·유효 범위·실패 신호 연결 |
| `competing_model` | 대안이 없거나 허수아비 | 가능한 대안 언급 | 같은 관찰을 실제로 설명하는 강한 경쟁 모델 구성 |
| `discriminating_test` | 어떤 결과에서도 판단을 못 바꿈 | 실행 가능한 검사이나 모델 차이가 약함 | 경쟁 모델이 다르게 예측하고 결과별 수정 규칙이 명확 |
| `adverse_evidence_revision` | 반대 증거를 무시 | 한계·확신만 약화 | 전제·모델·범위·결론 중 하나 이상을 구체적으로 수정 |
| `plain_precise_link` | 비유·전문용어가 메커니즘 왜곡 | 쉬운 설명과 정밀 설명의 연결이 약함 | 쉬운 설명이 정밀한 관계·조건·예외를 보존 |
| `uncertainty_calibration` | 미확인 내용을 사실화 | 일반적인 주의 문구 | 미지·범위·변경 조건과 확신을 연결 |
| `actionability` | 결론이나 일반 조언만 있음 | 다음 단계가 있으나 기준이 모호 | 즉시 실행 조치, 통과·중단 조건 또는 다음 판별 검사 구체적 |
| `efficiency` | 과도한 체크리스트 또는 핵심 누락 | 다소 장황·중복 | 결론을 바꾸는 작업에 집중하고 출력은 위험에 맞게 압축 |

### 직접 작업으로 인정되는 증거

- 단계가 확인 가능한 유도·계산
- 단위와 입력이 있는 규모 추정
- 실행 로그가 있는 코드·테스트·벤치마크
- 행과 열의 의미가 분명한 데이터 비교
- 날짜·버전·원주장을 직접 대조한 출처 기록
- 변수와 교란 경로가 명확한 인과 도식
- 사전 통과 기준과 결과별 행동이 있는 실험·프로토타입

“검증해야 한다”, “자료가 필요하다”라는 제안만으로는 수행된 검사가 아니다. 실행할 수 없는 경우에는 `미검증`, 부족한 입력, 다음 판별 검사와 결과별 결론 변경 조건을 명시했는지 본다.

## 7. 결과 품질과 하드 실패

과정 점수와 별도로 다음을 평가한다.

- 기대 발견 탐지율
- 사실·논리·계산 오류 수
- 기준선 대비 정답 또는 의사결정 품질
- 반대 증거 포함률
- 결론 범위와 실제 근거의 일치
- 사용자가 재현·재검토할 수 있는 정도
- 토큰·시간·도구 호출 비용
- 불필요한 장문과 체크리스트 비용

다음 중 하나는 총점과 무관하게 실패 후보로 분류한다.

- 확인하지 않은 사실·출처·계산·실행 결과를 수행한 것처럼 조작
- 태그와 제목만 있고 적용 가능한 직접 작업 증거가 없음
- 어느 결과에서도 결론을 바꾸지 않는 검사를 강한 검증으로 제시
- 불리한 증거가 있는데 전제·모델·범위·결론·확신에 영향이 없음
- 수학적 사례를 증명으로 오인하거나 정의역·적용 범위를 벗어나 일반화
- 사회·조직 문제에서 사람·인센티브·제도·윤리를 삭제
- 고위험 작업에서 독립 검증·최신 권위 자료·전문가 검토 없이 강한 행동 결론 제시
- 스킬 사용 자체나 파인만의 이름을 정확성의 증거로 사용

## 8. 실행 기록

`run_evals.py`는 각 과제를 격리된 임시 Git 저장소에서 실행하고 전체 프롬프트를 표준 입력으로 `codex exec -`에 전달한다. `--json` trace, stderr, 최종 메시지와 프롬프트를 개별 artifact로 저장한다.

실행 전 작업 행렬만 확인:

```bash
python scripts/run_evals.py \
  --case software-perf-01 \
  --conditions baseline generic feynman feynman-implicit \
  --dry-run
```

반복 비교 실행:

```bash
python scripts/run_evals.py \
  --conditions baseline generic feynman feynman-implicit \
  --repeats 3 \
  --shuffle \
  --seed 20260902
```

`run-metadata.json`에는 다음을 남긴다.

- 스킬 버전과 패키지 SHA-256
- 저장소 commit SHA
- Codex CLI·Python·플랫폼 버전
- 조건·반복 수·sandbox·모델
- 무작위 실행 순서와 seed
- 스킬 설치·명시 호출 여부
- 종료 코드·타임아웃·실행 오류
- 사용량과 완료된 도구 이벤트 수
- 스킬 파일 참조 이벤트의 보조적 흔적

`skill_reference_event`는 trace 문자열 기반 보조 신호일 뿐 자동 발동의 완전한 증거가 아니다. D 조건의 행동 점수와 함께 해석한다.

## 9. 두 종류의 블라인드 채점

### 9.1 모델 보조 구조화 채점

```bash
python scripts/grade_evals.py --run-dir evals/results/<run-id>
```

채점 프롬프트에는 조건명을 넣지 않고 사례의 기대 발견·행동 차원·하드 실패와 후보 답변을 전달한다. 구조화 출력은 `grading-schema.json`으로 제한한다.

모델 채점은 빠른 회귀 탐지에 유용하지만 최종 진실이 아니다. 후보와 채점기가 같은 계열이면 편향이 상관될 수 있으며, 미묘한 계산 오류나 형식 준수 가장을 놓칠 수 있다.

### 9.2 조건 블라인드 사람 검토

```bash
python scripts/prepare_blind_review.py --run-dir evals/results/<run-id>
```

생성물:

- `samples.jsonl`: 조건을 제거한 과제·후보·평가 메타데이터
- `scoring.csv`: 차원별 `0/1/2/NA` 입력 표
- `condition-key.json`: 채점 종료 후에만 여는 조건 키
- `REVIEW.md`: 검토 절차

채점 완료 전 `condition-key.json`을 열지 않는다. 제목과 파인만이라는 단어가 아니라 실제 계산, 경쟁 모델의 설명력, 검사의 판별력과 수정 효과를 평가한다.

모델 보조 채점과 사람 채점이 충돌하면 개별 trace, 입력, 계산과 출처를 재검토한다.

## 10. 일반 비판적 사고와의 차이 평가

C가 A보다 나은 것만으로 파인만 특이성을 입증하지 않는다. B와 C를 비교해 다음의 추가 효과를 본다.

- 작동 정의로의 재표현률
- 독립적인 대안 표현 생성률
- 직접 계산·규모 추정·작은 사례 수행률
- 경계·극한·실패 입력 사용률
- 경쟁 모델을 실제로 구별하는 검사 비율
- 불리한 결과에 따른 모델 수정률
- 쉬운 설명과 정밀 근거의 일치도

B와 C가 비슷하면 스킬을 더 짧은 일반 검증 스킬로 축소하거나 파인만 특이 행동을 강화할지 검토한다.

D는 C보다 낮을 수 있다. 그 차이는 스킬 본문 품질뿐 아니라 description의 발동 정확도와 플랫폼의 스킬 선택 동작을 함께 반영한다.

## 11. 수용 기준

최소 수용 기준은 다음과 같다.

- 정적 validator 통과
- 명시 호출 사례에서 핵심 루프의 적용 가능한 차원이 평균 1.5/2 이상
- 조작된 작업 결과와 고위험 과잉 확신 같은 하드 실패 0건
- C가 A보다 기대 발견·직접 점검·판별 검사·수정률에서 개선
- C가 B보다 파인만 특이 지표 중 적어도 일부에서 일관된 추가 효과
- D의 암묵 발동 미탐·오탐을 사례별로 기록하고 description 회귀에 연결
- 품질 향상이 토큰·시간·도구 비용 증가에 비해 실질적 가치가 있음

표본이 작거나 반복 간 분산이 크면 “성능 검증 완료”가 아니라 `예비 결과`로 보고한다.

```text
발동 정밀도·재현율:
조건별 일반 점수:
조건별 파인만 특이 점수:
기대 발견 탐지율:
하드 실패와 최악 사례:
토큰·시간·도구 비용:
모델 채점과 사람 채점의 차이:
현재 결론과 확신:
가장 큰 한계:
다음 회귀 사례:
```

평균뿐 아니라 사례별 분산과 최악 실패를 보존한다. 조건별 원자료와 채점 근거를 함께 저장한다.

## 13. 버전 관리

실제 실패 사례를 발견하면 다음을 남긴다.

```text
프롬프트:
기대 행동:
실제 행동:
실패 원인:
수정한 규칙:
새 회귀 검사:
수정 전후 비교:
```

최소한 하나의 실제 실패가 해결되었거나 명확한 기능이 추가되었을 때 버전을 올린다. 평가 결과가 개선되지 않거나 비용 대비 효과가 낮으면 규칙을 줄이거나 삭제한다.
